# 代替案 B：既存の bash 互換ツールを持ち込む

**この資料を出す場面**：「自作ツールを保守したくない」「Git Bash でよいのでは」と言われたとき。

## 1. 一言で

自作せず、既にある bash 互換の実行バイナリを実行機に置く方式。開発工数はゼロ。
論点は技術ではなく、持ち込み審査・挙動の統制・保守主体の 3 つになる。

## 2. 候補（2026 年 11 月時点の調査）

各プロジェクトの公開説明に基づく。版・ライセンス・Windows での成熟度は採用前に一次情報で確認すること。

| 候補 | 種別 | 公開説明の要点 | この用途での注意 |
|---|---|---|---|
| Git for Windows（Git Bash） | 本物の bash（MSYS2 ベース） | — | 互換性は最も高い。パスと引数の自動変換（MSYS の変換層）の癖を知っておく必要がある。Git を入れている端末には既にある |
| [busybox-w32](https://github.com/rmyorston/busybox-w32) | 単一 EXE に多数の Unix コマンドとシェルを収めたもの | Windows の WIN32 API への BusyBox 移植。シェルは ash ベースで POSIX 互換を目指し、bash の機能の一部に対応 | シェルは bash ではない。配列など bash 固有機能を使うスクリプトは動かない場合がある |
| [bashy](https://github.com/qiangli/bashy) | Go 製の bash 互換シェル（単一バイナリ） | Bash 5.3 互換をうたう。Windows でもビルド・動作するが、テストスイートの完走は確認中と記載 | Windows での検証状況を要確認 |
| [niubash](https://github.com/unixwin/niubash) | Windows ネイティブの bash 互換シェル | MSYS2・Cygwin・WSL を使わず、パス変換層を持たないと説明 | 採用実績と保守体制を要確認 |
| [PsBash](https://github.com/standardbeagle/ps-bash) | bash → PowerShell 変換＋PowerShell モジュール | WSL や Git Bash 無しで bash コマンドを PowerShell に変換して実行。70 個超のコマンドを PowerShell 側で提供 | 代替案 A の既製品にあたる。PowerShell 7 系が前提かを要確認 |
| [just-bash（Python 版）](https://pypi.org/project/just-bash/) | 純 Python の bash インタープリター | AI エージェント向けのサンドボックス。仮想ファイルシステム上で動き、ネイティブ実行をしない設計。プレリリース。Python 3.11 以上 | 目的が違う（隔離実行）。EXE を呼ぶバッチには使えない |
| Microsoft の Windows 向け Coreutils | `ls` `cp` `rm` `cat` などのネイティブ版 | 2026 年の開発者会議で一般提供が発表されたと報じられている | シェルではなくコマンド群。PowerShell から Unix コマンドを使えるようにする方向の補完策 |

出典：各リンク先の README／パッケージ説明、および Windows 向け Coreutils については
[WebProNews の記事](https://www.webpronews.com/microsoft-brings-native-unix-core-utilities-to-windows-in-major-developer-push/)。

## 3. 本命案（自作インタープリター）と比べて

### 同じように提供できること

| 項目 | 内容 |
|---|---|
| bash スクリプトがそのまま動く | Git Bash なら互換性は本物。自作より高い |
| Unix コマンド群 | 同梱されている |
| 性能 | ネイティブ実装なので、ループやテキスト処理は自作より速い |
| スクリプト資産 | 共通。本命案とどちらでも同じスクリプトが使える（撤退・乗り換えが容易） |

### 実現できなくなること・増える負担

| 項目 | 内容 |
|---|---|
| 持ち込み審査 | 実行バイナリ（Git for Windows は多数の EXE と DLL）を閉域へ入れる審査が要る。本命案はテキストのソース一式 |
| 挙動の統制 | 改行・文字コード・パス変換・終了コードの扱いは持ち込んだツールの仕様に従う。自社の事情に合わせて変えられない |
| 不具合時の対応 | 修正は上流待ちか、回避策で対応 |
| 監査性 | 「何が入っているか」を自分たちで読んで確認する範囲が大きくなる |
| セキュリティ製品との相性 | 未知の実行バイナリは誤検知の対象になりうる。実機で確認が要る |
| 版の固定 | ツールの更新で挙動が変わりうる。更新のたびに回帰確認が要る（本命案の `tests/golden` はその確認にも使える） |

## 4. この案を選ぶ目安

| 状況 | 判断 |
|---|---|
| 全実行機に Git for Windows が既に入っていて、運用部門がバッチ実行に使うことを認めている | この案が最安。自作は不要 |
| 実行機へ新しいバイナリを入れる審査が重い／通らない | 本命案 |
| bash 固有機能を使わない単純なスクリプトで、単一 EXE なら持ち込める | busybox-w32 を評価 |
| 改行・文字コード・終了コードの扱いを自分たちで決めたい | 本命案 |

## 5. 併用という選択

スクリプトは共通なので、開発 PC では Git Bash、実行機では bashwin、という併用もできる。
その場合、`tests/run_golden.py` を両方の環境で流しておくと、挙動差を事前に把握できる。

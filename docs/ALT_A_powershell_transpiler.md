# 代替案 A：Bash → PowerShell トランスパイラー

**この資料を出す場面**：「実行機に Python は置けない」「成果物は .ps1 でないと運用が受け取れない」と言われたとき。

## 1. 一言で

bash で書いたスクリプトを、開発側で PowerShell に変換してから配る方式。実行機に要るのは PowerShell だけになる。
ただし変換できるのは bash の一部（制御構造と EXE の呼び出し）に限られる。

## 2. 本命案（インタープリター）と比べて

### 同じように提供できること

| 項目 | 内容 |
|---|---|
| bash の制御構造 | `if/elif/else` `case` `for` `while` `&&` `\|\|` `!` |
| スカラー変数と引用された展開 | `x=...` `"$x"` `"${x:-既定値}"` |
| 条件判定 | `[ ]` `[[ ]]` の文字列・数値・ファイル判定 |
| 関数と引数 | `f() { ...; }` `$1` `"$@"` `return` |
| ネイティブ EXE の呼び出しと終了コード | `"$APP" --opt "$arg"`、`set -e` 相当の検査 |
| 実行前の検査 | 構文チェック（`-n`）、使用コマンドの棚卸し（`--inventory`）は共通パーサで同じものが使える |
| 実行機の前提 | Python 不要。Windows 標準の PowerShell だけ |

### 実現できなくなること

| 失うもの | 理由 |
|---|---|
| パイプライン（`a \| b`） | PowerShell のパイプはオブジェクトを流す。ネイティブ同士でもテキストを再エンコードする版があり、バイト列がそのまま流れない |
| `grep` `sed` `awk` `sort` などのテキスト処理 | PowerShell 側に存在しない。別途バイナリを置くか、PowerShell の書き方に直すことになる |
| 無引用の展開（`for f in $LIST`） | 単語分割とパス名展開は bash 固有の意味 |
| 配列・連想配列、ヒアドキュメント、`$(...)` の複合利用、サブシェル、`trap` | 対応づけが 1 対 1 にならない |
| bash との突き合わせによる検証 | 「変換結果が同じ意味か」を確かめる段が 1 つ増える |
| 既存スクリプト資産の流用 | サブセットに書き直す必要がある |

### 実測：どれだけのスクリプトが対象になるか

生成器そのものを判定器として使って測った（[VERIFICATION.md](VERIFICATION.md) 5 章）。

| 対象 | 変換可能 |
|---|---:|
| 機能網羅のために書いたテストコーパス 478 件 | 56 件（11.7%） |
| うち実務を模したスクリプト 37 件 | 0 件 |
| 変換可能な範囲だけで書いた検証用ケース 16 件 | 16 件 |

実務を模したスクリプトが 0 件なのは、どれも `grep`／`sed`／パイプライン／`read` のいずれかを使っているため。
この案が合うのは「EXE を順に呼び、終了コードで分岐する」ジョブに限られる、という判断は変わらない。

手元のスクリプトで測るには：

```
python bashwin.pyz --ps1-check job.sh
```

変換できれば終了コード 0、できなければ 1 と、妨げている構文の行番号・種類を出す。

## 3. PowerShell 側の落とし穴（生成器を作るなら必ず踏む箇所）

一般に知られた挙動を挙げる。版によって違うので、対象の実行機で再確認すること。

| 箇所 | Windows PowerShell 5.1 | 影響 |
|---|---|---|
| `>` によるリダイレクト | 既定で UTF-16LE で書かれる | ネイティブコマンドの出力をファイルへ落とすと文字コードが変わる |
| ネイティブコマンドへの引数 | 二重引用符を含む引数や空文字列の引数が正しく渡らない場合がある | 引数の内容が変わる・消える |
| 成否の判定 | `$?` と `$LASTEXITCODE` が別。`$ErrorActionPreference` はネイティブの終了コードを見ない | `set -e` 相当は呼び出しごとに検査コードを生成する必要がある |
| `&&` `\|\|` | 5.1 には無い（7 以降） | `if` に展開する |
| 実行ポリシー | 既定では .ps1 の実行が制限されうる | 署名か、組織のポリシー設定が要る |
| ネイティブ同士のパイプ | テキストとして再解釈される | バイナリや文字コードが壊れる |

これらを避けて忠実に動かすには、PowerShell 側に実行時ライブラリ（プロセス起動、バイト透過の入出力、終了コード管理）を持つことになる。
そうなると生成物は「読める PowerShell」ではなくなる。既存の同種ツールも、変換器に加えて PowerShell 側のモジュールを同梱する構成を取っている（[ALT_B](ALT_B_existing_binaries.md) の PsBash）。

## 4. 現状

| 項目 | 状態 |
|---|---|
| 共通パーサ（bash → AST） | 実装済み。インタープリターと共用 |
| 生成器（`--ps1`）と判定（`--ps1-check`） | 実装済み（第 1 段：制御構造・スカラー変数・条件・関数・外部 EXE・出力リダイレクト） |
| ランタイム（生成物に埋め込む PowerShell、約 1,000 行） | 実装済み |
| 静的検査（`tests/test_ps1_static.py`） | 全項目通過 |
| 実行検証ハーネス（`tests/run_ps1.py`） | 実装済み |
| **生成物の実行検証** | **未実施**。作業環境で PowerShell の起動が拒否されたため |

使い方・対応範囲・bash との差異・実機での測定手順は [TRANSPILER.md](TRANSPILER.md)。

当初は「実行して確かめられないコードは出さない」として生成器を見送っていた。今回は依頼を受けて実装したが、
実行検証できていない事実は変わらない。**実機で `tests\run_ps1.py` が通るまでは未検証品として扱うこと。**

次の段で広げる候補（優先は実機検証の結果を見てから決める）：パイプライン（逐次・メモリ内）、`read`／`printf`、
入力リダイレクトとヒアドキュメント、サブシェル、無引用展開の単語分割、ファイル名展開、`${x#p}` `${x%p}`、配列。

## 5. この案を選ぶ目安

| 状況 | 判断 |
|---|---|
| ジョブの中身が「EXE を順に呼び、終了コードで分岐する」だけ | 向いている。`--ps1-check` で確認 |
| テキスト加工や集計をシェルでやっている | 向かない。本命案か、加工部分を別プログラムにする |
| Python は置けないが、単一の実行バイナリなら置ける | 代替案 B を先に検討 |

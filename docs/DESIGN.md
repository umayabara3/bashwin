## 1. 俯瞰と判定

### 1.1 問題の分解

「PowerShell が bash に劣る」と感じる中身は 3 つに分かれる。

1. **言語**：テキストとパイプ中心の書き方、クォートと展開、`set -e`、関数の合成
2. **道具**：`grep` `sed` `awk` `sort` `find` などの小さなフィルタ群
3. **資産**：既存の bash スクリプト、書ける人、レビューできる人

どの方式でも、この 3 つをどこまで持ち込めるかが評価軸になる。

### 1.2 選択肢

| 案 | 中身 | 言語 | 道具 | 資産 | 実行機に要るもの |
|---|---|---|---|---|---|
| **竹（本命）** | 純 Python の Bash インタープリター＋内蔵コマンド | ◎ | ◎（74 個内蔵） | ◎ そのまま動く | Python |
| 松 | 竹＋ Bash→PowerShell トランスパイラー | ◎ | ◎ | ◎ | Python（変換物は PowerShell のみ） |
| 代替 A | Bash→PowerShell トランスパイラーのみ | △ サブセット | × | △ 書き直しが要る | PowerShell のみ |
| 代替 B（梅） | 既存の bash 互換バイナリを持ち込む | ◎ | ◎ | ◎ | 持ち込んだバイナリ |

### 1.3 判定：インタープリターを本命にする

**理由 1：意味論を翻訳せずに実行できる。**
bash と PowerShell は、パイプを流れるもの（バイト列／オブジェクト）、変数展開（単語分割あり／なし）、
成否の表現（`$?`／`$?` と `$LASTEXITCODE`）が根本から違う。
トランスパイラーで忠実さを求めると PowerShell 側に bash の実行時ライブラリを持つことになり、
生成物は読めないコードになる。それは「可読性・保守性」という目的に反する。

**理由 2：測れる。**
インタープリターは「同じスクリプトを本物の bash と両方で実行し、出力と終了コードを比べる」だけで検証できる。
トランスパイラーは「変換結果が元と同じ意味か」をもう 1 段挟むため、検証が遠くなる。

**理由 3：代替 A の適用範囲を実測すると狭い。**
テストコーパス 475 件を「PowerShell へ意味を変えずに機械変換できる範囲」の判定器にかけた結果、
収まったのは **50 件（10.5%）**。実務を模したスクリプト 37 件では **0 件**だった
（[VERIFICATION.md](VERIFICATION.md) 5 章）。妨げの上位は Unix コマンドの使用、パイプライン、無引用の展開。

**理由 4：閉域・ポータブル運用に合う。**
本体はテキストのソース一式で、既存の `python.exe` の上で動く。新しい実行バイナリを持ち込まない。

### 1.4 代替案へ切り替える条件

| こう言われたら | 見せる資料 | 要点 |
|---|---|---|
| 「実行機に Python は置けない」「成果物は .ps1 でないと受け取れない」 | [ALT_A](ALT_A_powershell_transpiler.md) | 制御構造と EXE 呼び出しだけなら可能。パイプ・テキスト処理は失う |
| 「自作ツールを保守したくない」「Git Bash でよいのでは」 | [ALT_B](ALT_B_existing_binaries.md) | 互換性と性能は上。持ち込み審査と挙動の統制が論点 |

### 1.5 松の到達状況

松のうち**トランスパイラーの生成器は実装していない**。実装したのは共通パーサ上の「変換可能性チェッカ」（`--ps1-check`）まで。
理由：生成した PowerShell を実行して確かめる環境が今回の作業環境に無く、実行検証できないコードは出さないと判断した。
詳細と着手条件は [ALT_A](ALT_A_powershell_transpiler.md)。

## 2. 構成

```
script.sh ──► parser.py ──► AST (nodes.py) ──┬─► interp.py      実行（本命）
                                             ├─► inventory.py   使用コマンドの棚卸し
                                             └─► ps_subset.py   PowerShell 変換可能性の判定

interp.py ─ expand.py     語の展開（ブレース→チルダ→変数/コマンド/算術→単語分割→グロブ）
          ─ arith.py      算術式（64bit 整数、C と同じ切り捨て）
          ─ pattern.py    グロブ→正規表現、POSIX 正規表現→Python re
          ─ shbuiltins.py シェル組み込み 53 個（cd, read, printf, trap, getopts …）
          ─ applets/      内蔵コマンド 74 個（textutils, sed, awk, fileutils, sysutils, archive）
          ─ osdep.py      OS 依存部（コマンド探索、起動方法、パス対応付け、終了コード）
          ─ timefmt.py    OS に依存しない日時書式
```

規模は Python 約 13,000 行。外部ライブラリは使っていない。

### 2.1 パーサ

手書きの再帰下降。スクリプト**全体を先に解析してから**実行する（bash は 1 コマンドずつ読んで実行する）。
構文エラーがあれば 1 行も実行せずに終了コード 2 で止まる。途中まで実行して止まるより安全側と判断した設計差異。

### 2.2 展開

展開の途中結果を「フラグメント」（文字列、引用済みか、分割対象か）の列で持つ。
`"$@"` が作るフィールド境界、`"${x:-}"` が作る空フィールド、無引用の展開だけに起きる単語分割とグロブを、
この 3 属性で区別する。

### 2.3 実行エンジン

AST を直接たどる。制御の飛び（`break` `continue` `return` `exit`）は Python の例外で表す。
`set -e` は「条件文脈の深さ」を数えて、bash と同じ箇所でだけ発動させる。

## 3. Windows を前提にした設計判断

| 論点 | 判断 | 理由 |
|---|---|---|
| fork が無い | サブシェル・パイプライン各段・`$(...)`・`&` は、インタープリター状態の複製を**スレッド**で動かす | 本物のプロセスにするのは外部コマンドだけ。プロセス生成が重い Windows で速い |
| カレントディレクトリ | プロセスの cwd は変えない。インタープリターごとに論理 cwd を持ち、ファイル操作は絶対パスに解決する | スレッド間で cwd を共有しないため。`( cd x; ... )` が親に漏れない |
| ファイル記述子 | fd 番号→ファイルの表をインタープリターごとに持つ | リダイレクトをスレッド安全にするため |
| 入出力 | すべてバイナリ・無バッファ。パイプはバイト透過 | 改行変換や文字コード変換で内容を壊さない |
| `read` の読み過ぎ | 通常ファイルは塊で読んで seek で戻す。パイプは 1 バイトずつ | 同じ入力を後続コマンドが読めるようにする（bash と同じ） |
| パス区切り | `/` を正とする。`\` は bash ではエスケープ文字なので、使うなら引用する | bash の文法を変えない |
| パスの書き換え | bashwin 自身が開くパスだけ `/dev/null`→`NUL`、`/tmp`→一時フォルダ、`/c/x`→`C:/x` に対応付ける。**外部コマンドの引数は書き換えない** | MSYS 系の「暗黙の引数変換」は事故の元。変換が要るときは `winpath` で明示する |
| 改行 | スクリプトの CRLF は読み込み時に受け入れる。出力は LF。Windows では `igncr` を既定で有効（`$(...)` と `read` が行末の CR を落とす） | Windows のコマンドは CRLF を出す。`$(cmd)` に `\r` が残る定番の事故を防ぐ |
| 文字コード | 内部は Unicode。入出力は `BASHWIN_ENCODING`（既定 UTF-8）で、不正バイトは保持（surrogateescape） | cp932 のデータを壊さない。変換は `iconv` で明示 |
| 終了コード | 0〜255 に正規化。下位 8bit が 0 でも元が非 0 なら 255 にする。生の値は `$BASHWIN_RAWSTATUS` | Windows の終了コードは 32bit。256 が 0（成功）に化ける事故を防ぐ |
| コマンド探索 | `PATH`（`;` 区切り）と `PATHEXT`。`.exe` は直接、`.cmd/.bat` は `cmd.exe /d /s /c`、`.ps1` は `powershell.exe -File`、`.sh` と sh/bash の shebang は**プロセス内で別シェルとして**実行 | `.ps1` に実行ポリシー回避フラグは付けない（統制は環境側に従う） |
| 深い再帰 | 本体は大きなスタックのワーカースレッドで動かす | Windows のメインスレッドは既定 1MB |
| 危険操作 | `rm -rf /`（ドライブのルート）は拒否。`tar` `unzip` は展開先の外へ出るパスを拒否 | バッチの事故防止 |

## 4. bash 互換の作り方

仕様書を読んで実装するのではなく、**本物の bash を基準器にして差分で詰めた**。
テストケースは `tests/spec/*.sh` に `#### 名前` 区切りで書き、`tests/run_diff.py` が bash と bashwin の両方で実行して比べる。
bashwin 側の `PATH` には Python しか置かないので、内蔵コマンドだけで動いていることも同時に確かめられる。

この方法で見つかった、仕様書からは気づきにくい挙動の例：

- 展開エラー（`$((1/0))`、readonly への代入）で、bash は**その行の残りを捨てて**次の行から続行する。`set -e` でも終了しない
- `"${x:-}"` は空でも 1 個の引数になる（`[ -n "${x:-}" ]` が偽になるために必要）
- `shopt -s nullglob` のとき、閉じていない `[` はグロブではない（`[ "$x" -gt 0 ]` の `[` が消えてはいけない）
- `printf '%-14s'` の幅はバイト数で数える
- サブシェル内の `trap -p` は親の trap を表示する

いずれも実装後のテストで不一致として現れ、修正した。テストに無い組み合わせには未発見の不一致が残っている前提で扱う。

役割×時間軸の確認表と立場ごとの使い方は [OPERATIONS.md](OPERATIONS.md)。設計に反映した点：

| 撤退 | スクリプトは普通の bash。Git Bash・WSL・Linux へそのまま持っていける |

## 6. 既知の限界

1. **Windows 実機で実行していない。** Windows 用の分岐は机上確認とシミュレーションまで。最初に `tests/run_golden.py` を実機で流すこと
2. 速度は bash の 1/15 程度（ループ、大量テキスト）。プロセス起動が支配的な処理はほぼ同等。[VERIFICATION.md](VERIFICATION.md) 6 章
3. 対話シェルではない（プロンプト、補完、ジョブ制御なし）
4. 内蔵コマンドは GNU 版のよく使うオプションに限る。無いオプションはエラーになる
5. `>( )`、`select`、`extglob`、nameref、`export -f`、DEBUG/RETURN トラップは非対応

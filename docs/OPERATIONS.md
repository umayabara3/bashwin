# 運用ガイド

## 1. 自分は結局どう使うのか（立場別）

### スクリプトを書く人

1. いつもどおり bash で書く。`#!/bin/bash` と `set -euo pipefail` から始める
2. 書いたら構文検査：`python bashwin.pyz -n job.sh`
3. 何に依存しているか確認：`python bashwin.pyz --inventory job.sh`
   - 「external commands」に出たものは実行機に必要（`java` `sqlplus` など）
   - 「bashwin applets」に出たものは内蔵なので何も要らない
4. 動かす：`python bashwin.pyz job.sh 引数...`
5. Windows のパスは `/` で書く（`C:/data/in`）。`\` を使うなら引用する（`'C:\data\in'`）
6. Windows のコマンドにパスを渡すときに `\` 区切りが要るなら `$(winpath -w "$p")`

迷ったら [COMPATIBILITY.md](COMPATIBILITY.md) の「未対応」と「bash との差異」を見る。

### ジョブを定義・監視する人（JP1 など）

ジョブ定義にはこの形で書く。ランチャー（.cmd）は挟まない。

```
実行ファイル: C:\tools\python\python.exe
パラメーター: C:\tools\bashwin\bashwin.pyz D:\jobs\nightly_job.sh 引数...
```

| 知りたいこと | 答え |
|---|---|
| 正常・異常の判定 | 終了コード。スクリプトの `exit N` がそのまま返る。0 が正常 |
| 標準出力・標準エラー | スクリプトの出力がそのまま出る。文字コードは既定 UTF-8、改行は LF |
| 構文エラーのとき | 1 行も実行せず終了コード 2。標準エラーに行番号つきメッセージ |
| コマンドが無いとき | そのコマンドが 127 を返す。`set -e` なら 127 で終了 |
| bashwin 自体の内部エラー | 終了コード 70 と Python のトレースバック |
| 強制終了したとき | 実行中の外部コマンドは別プロセスなので、ジョブ管理側の強制終了が子プロセスに届くかを実機で確認する |
| ログを cp932 で見たい | ジョブの環境変数に `BASHWIN_ENCODING=cp932` を設定する（データの解釈も cp932 になる点に注意） |

### 本体を保守する人

- 変更したら Linux で `python3 tests/run_diff.py`（bash との突き合わせ）。全件一致を確認してから配布物を作り直す
- 不具合報告を受けたら、まず再現スクリプトを `tests/spec/` に 1 ケース追加する。bash の出力が正解になる
- 内蔵コマンドを足すときは `bashwin/applets/` に関数を書き、`applets/__init__.py` の `register` に名前を足し、テストを同時に追加する

### 持ち込み・変更を審査する人

- 審査対象はテキストのソース一式（Python 約 13,000 行）と、それを固めた `bashwin.pyz` 1 ファイル
- 外部ライブラリなし。ネットワーク通信なし。実行時に AI を呼ばない
- 何を実行できるか：スクリプトが呼ぶ外部コマンドは `--inventory` で事前に列挙できる。ただし「dynamic command names」に出た行は名前が実行時に決まるので目視が要る
- 危険操作の歯止め：ドライブのルートへの `rm -rf` 拒否、アーカイブ展開時の外側パス拒否。それ以外のファイル操作はスクリプトの権限どおりに実行される

## 2. 役割×時間軸の確認表

空欄を作らないことを目的にした表。「—」は該当する作業が無いことを確認済みの意味。

| 時点 | スクリプトを書く人 | ジョブを運用する人 | 本体を保守する人 | 審査する人 |
|---|---|---|---|---|
| **初回** | Python の場所を確認。`-n` と `--inventory` を通す。小さな入力で試走 | ジョブ定義に `python.exe bashwin.pyz script args` を登録。終了コード判定を設定 | Windows 実機で `tests/run_golden.py` を流し、不一致を修正してから配布 | ソース一式と pyz を審査。`--inventory` の出力を確認 |
| **2 回目以降** | スクリプトだけ差し替える。本体は触らない | 変更なし | — | スクリプト差分と `--inventory` 差分を見る |
| **差し戻し** | 前版のスクリプトに戻す。スクリプトは状態を持たないので戻すだけ | ジョブ定義は変えない | 本体起因なら旧版 `bashwin.pyz` に置き換える（1 ファイル） | 差し戻し後の版を記録 |
| **途中中断** | `trap ... EXIT` で一時ファイルとロックを片付ける書き方にする。再実行して安全か（冪等か）を自分で確認する | 強制終了後、ロックファイルと作業ファイルの残りを確認して再実行 | 中断時の挙動に不具合があれば再現ケースを追加 | — |
| **ツール更新** | 更新後に自分のスクリプトを `-n` で再検査 | 検証環境で主要ジョブを 1 周してから本番へ | `run_diff.py`（Linux）と `run_golden.py`（Windows）を両方通す。`--version` を上げる | 版の差分を審査。pyz のハッシュを記録 |
| **棚卸し** | 自分のスクリプトの `--inventory` を取り直す | 稼働中ジョブ一覧と呼び出しスクリプトを突き合わせる | `--applets` の一覧と、使われていない内蔵コマンドを確認 | 外部コマンド依存の一覧を更新 |
| **肥大** | 共通関数は `lib.sh` にまとめて `source` する。1 スクリプト 1 役割を保つ | ログは出力先の保持期間で管理（bashwin 自体はログを溜めない） | 内蔵コマンドの追加はテスト同伴に限る。大きい機能（例：対話機能）は入れない | 行数とコマンド数の増え方を見る |
| **引き継ぎ** | スクリプト冒頭に用途・引数・終了コードを書く | ジョブ定義書に実行形式と Python の場所を書く | DESIGN.md 2〜4 章と tests の使い方を渡す。基準器は bash という 1 点を伝える | 審査記録を渡す |
| **撤退** | スクリプトは普通の bash なので、Git Bash・WSL・Linux へそのまま移せる。`winpath` と `$BASHWIN_*` を使った箇所だけ直す | ジョブ定義の実行ファイルを差し替える | リポジトリを凍結。golden は移行先の検証にも使える | 持ち込み台帳から外す |

## 3. 書き方の指針（事故を減らす）

| やること | 理由 |
|---|---|
| 変数は必ず `"$var"` と引用する | 空白入りパス（`C:/Program Files`）で壊れない |
| `set -euo pipefail` を先頭に置く | 失敗を見逃さない |
| 終了コードは 0〜125 の範囲で自分で決める | 126 以上はシェルが使う |
| Windows のコマンド出力を `$(...)` で受けるときは、そのまま使ってよい | 行末の CR は既定で落ちる（`igncr`） |
| 日本語を含むファイルの文字コードを意識する | 既定は UTF-8。cp932 のファイルは `iconv -f CP932 -t UTF-8` で変換してから処理する |
| `.cmd` / `.bat` に渡す引数に `%` `^` `&` を入れない | cmd.exe が解釈する |
| 外部コマンドの終了コードを厳密に見たいときは `$BASHWIN_RAWSTATUS` | 255 を超える値が丸められる前の値 |
